# 主張のラベル則

> 正本。プロジェクト固有ファイルに転記せず、ここを参照する。2026-09-28 のリセットで持ち越した。
> 由来: 旧 loop_agent プロジェクト（Claude Fable 5）の「根拠と基準版の列」規律。
> 外部でも独立に同型の規約（`VERIFIED` / `REASONED` / `ASSUMED`）が確立されている。

## なぜ必要か

コードやデータに関する主張は、根拠の強さが3段階に分かれる。**この3段階が混ざると、最も弱い主張が最も強い主張と同じ見た目になる。** そして混ざったことは事後に検出できない。

とくに危険なのは、ニッチなライブラリの API 名やシグネチャである。訓練データの被覆が薄い領域では、**もっともらしい捏造が起きる。** 構文としては正しく、名前としては自然で、存在しない。

## ラベル

| ラベル | 意味 |
|---|---|
| `実測` | 実際に実行した。出力を見た |
| `ソース行確認済` | ソースコードまたは一次資料の該当行を読んだ。`file:line` を示せる |
| `未確認` | 上記いずれでもない。推論・記憶・一般論 |

**CL-1. コードおよびデータに関する主張には、必ずいずれかのラベルを付ける。**

**CL-2. 無断の昇格を禁止する。** 推論を「ソース行確認済」と書かない。ソースを読んだことを「実測」と書かない。**diff は主張であり、実行が証拠である。**

**CL-3. `未確認` を含む修正案を、デバッグ中に出さない。** ソースを読むか、実行するまで黙る。デバッグ中の推測は、正しい可能性がある分だけ有害である（検証コストを人間に転嫁し、外れたときに切り分けを壊す）。

**CL-4. エラー全文（スタックトレース含む）が文脈に入る前に、原因を断定しない。** 抜粋からの断定は、抜粋に含まれなかった箇所を無視した推測である。

**CL-5. 外部ライブラリの API を使うコードには、参照ソースの `file:line` を併記する。** 示せない API は使わない。

**CL-6. 「1つのソースで見つからない」を「存在しない」と結論しない。** 索引の欠落と実体の不在は別である。

## 参照する版を固定する

**CL-7. `file:line` の根拠にする参照ソースは、使用中の版に固定する。**

`main` ブランチの HEAD はリリースタグより先に進んでいる。**実測例: 参照クローンの `main` が、使用中バージョンのタグより23日先だった。** 固定前は、リリース後のコミットを読んで `file:line` を示していたことになる。

**CL-8. 版の一致はタグ名だけに依存しない。** タグは付け替えられる。ソース内のバージョン記述（`.csproj` の `<Version>` など）と突き合わせる。

## 出所の帰属は別の軸である

**CL-9. 「自分がどう確かめたか」（本ファイルのラベル）と「原典が何を述べたか」（出所の帰属）を混同しない。**

ソースを読んで得た記述を、推論で別の対象に当てはめた場合、**読んだことは `ソース行確認済` だが、当てはめは推論である。** ラベルだけでは後者が記録されない。当てはめた部分は「推察」と明記する。

## 検証可能性

CL-3・CL-4 は、エラー出力の有無で機械的に判定できる。CL-5 は `file:line` の有無で判定できる。CL-7 は `git` の HEAD とタグの一致で判定できる。

**CL-1・CL-2・CL-6・CL-9 は prose 依存である。** ラベルなしの断定を見つけたら、人間が指摘する。これは予防できないので受け入れる。

## 適用範囲外

自然言語の要約、設計上の意見、選択肢の提示にはラベルを付けない。**ラベルはコードとデータの事実主張のためのものである。** 全文に付けると意味を失う。
