## なぜ必要か

モデル・相関式・近似には適用範囲がある。**範囲の外で使っても、例外は起きない。** もっともらしい数値が出て、形になり、誰も気付かない。

これはボクセル幾何が不正な形状でも例外を投げないのと同じ失敗様式であり、**検出手段が原理的に存在しない**類のものである。だから使用時ではなく**登録時**に範囲を書く。

## 書式

肯定と否定を対にし、**否定側を強い言葉で書く。**

> ○○・△△・□□には妥当だが、**××や◇◇に単独使用してはならない。**

原典の実例（第一次近似の質量/ΔV モデルについて）:

> 上昇損失が定数推定（±数百 m/s の不確かさ）。軌道積分なし。Isp 一定近似。eps 一定でスケール則を無視。
> → **相対比較・クロージャループ骨格・アーキテクチャ検証には妥当。要求確定や機体コミットに単独使用してはならない。**

**肯定だけを書くと、書かれていない用途が暗黙に許可される。** 否定を明記することで、範囲外使用が違反として可視化される。

## 基本規則

**VR-1. 相関式・近似モデル・経験式を登録するとき、適用範囲の欄を必須とする。** 空欄禁止。

**VR-2. 適用範囲が原典に書かれていない場合、欄を `null` にする。一般論で埋めない。** `null` の一覧が出てくること自体に価値がある（そこが知識の欠けている場所である）。

**VR-3. 適用範囲の外で使った結果は `未確認` として扱う。** `未確認` の値は最終成果物の生成に使わない。

**VR-5. 原典・文献の本文を転記しない。** 式または数値と、参照（式番号・箇条番号）だけを持つ。参照は**式番号まで**書く（ページ番号は版で動く）。

---

## 解除条件（ゲート）

**VR-4. 適用範囲を解除する条件を `validity_gate` 欄に書く。** 書けない場合は `null`。

原典の実例:

> 軌道3DOF積分・質量マージン方針・eps 根拠データの3点が揃うまで高忠実度化に進まない

**`validity_gate` を `note` に混ぜないこと。** 専用欄でないと一覧が取れず、「何が揃えば範囲が広がるか」を横断的に見られない。**ゲートの一覧は、次に何を調達すべきかの作業リストである。**

**参照だけが書かれていて本文がない場合も、ゲートの存在として扱う。** 同一の参照先を引く他項目の本文を採用してよい（`note` に参照だけを残すのは VR-4 違反である）。

## 出所の帰属

適用範囲の記述が「原典が直接述べたこと」なのか「原典の指摘を推論で当てはめたこと」なのかは、**別の情報である。** 混ぜると、推論が原典の記述として記録される。

**これは `claims_labeling.md` CL-2 の無断昇格と同型の誤りである。**

| `limitations_basis` | 意味 |
|---|---|
| `explicit` | 原典がその量について直接述べている |
| `inferred` | **原典の指摘が、推論によってその量に当てはまる** |
| （欄なし） | `limitations` が `null` の場合 |

**VR-8. `limitations_basis` を必須とする**（`limitations` が `null` の場合を除く）。**原典の指摘を推論で対応づけた場合は `inferred` とし、`limitations_inference` に推論経路を1行書く。** `explicit` と `inferred` を同じ欄に混ぜない。

### VR-8 の運用基準

> **`inferred` と書けるかどうかは、推論経路が1行で書けるかで判定する。** 書けなければ `null` である。

実測例: ある量について、原典が述べた「質量項の未計上」を根拠に `inferred` としようとしたが、**その量に固有の限界（1点のみの検査であること、高度変化の無視）とは別物であり、推論経路が書けなかった。** よって `null` に降格した。

**「関連はありそうだ」は推論経路ではない。** どの記述が、どの経路で、その量に及ぶのかを書けることが条件である。

**VR-9. 原典に無いが特定できた限界は `limitations_candidate` に書く。** `candidate_basis`（通常 `judgment`）と `candidate_author` を併記する。

**`limitations_candidate` は VR-1 の必須要件を満たさない。VR-3 の判定では `null` と同じ扱いとし、範囲外使用の検査は効き続ける。** 記録は残るが、根拠としては使えない。

> **候補の一覧は、知識の欠けている場所を示す地図である。** 文献で埋めるべき箇所がここに現れる。捨てないこと。

**VR-10. 粒度は「独立した `limitations` を持てるか」で決める。** 持てるなら分ける。持てないなら畳む。

> 「独立した式かどうか」で判断すると主観になる。**限界が違えば別項目である。** これは検証可能な基準である。

## 識別と参照

**VR-11. 不変アーカイブを参照するすべての欄に、パスに加えてハッシュを持つ。**

対象は式の出所だけではない。**限界の出所・ゲートの出所・その他の原典参照も同様である。**

パスは変わる。**実測例: 原典が2箇所に重複して存在し、一方を削除した結果、記録すべきパスが変わった。** また、フォルダのリネーム・日付プレフィックスの追加も実際に起きている。

**ハッシュはパスより強い識別子であり、かつ改変の検出にもなる。** 不変であるはずのアーカイブが編集されていれば、ハッシュ不一致で分かる（実測済み）。

### VR-11a. 参照は `source_refs` に集約し、ハッシュの分岐を起こさない

```jsonc
"source_refs": [
  { "id": "src",  "path": "...\\rocket.py", "lines": "67-71",
    "sha256": "...", "referenced_by": ["form"] },
  { "id": "lim",  "path": "...\\06_....md", "lines": "41",
    "sha256": "...", "referenced_by": ["limitations"] },
  { "id": "gate", "path": "...\\06_....md", "lines": "46",
    "sha256": "...", "referenced_by": ["validity_gate"] }
]
```

各欄は `source_refs[].id` を引く（`limitations_ref` / `validity_gate_ref`）。

**統合の判定は行で決める。**

- **行が同一** → 1エントリに統合し、`referenced_by` に複数列挙する
- **行が違う** → **エントリを分ける。** 同一ファイルでも構わない

> **`lines` を範囲に丸めてはならない。** 限界が 42-43 行、ゲートが 46 行のとき `42-46` と書くと、**限界の出所が 46 行目まで含むという偽の主張になる。** VR-5 が要求する参照精度に反し、CL-2 の無断昇格に当たる。
>
> 実データでは、ゲートを持つ4本すべてで行が違っていた。**「ファイルが1つならハッシュも1つ」は、行が一致した特殊例からの過剰一般化だった。**

**VR-11b. ハッシュの分岐防止は、文言ではなく機械検査で担保する。**

VR-11a が本来防ぎたいのは「同一ファイルに対して複数の異なるハッシュ値が記録される」事故（1本だけ直し忘れる）である。**これは検査できる。**

| 検査 | 見ているもの | 実測で確認された役割 |
|---|---|---|
| ハッシュ照合 | **記録 vs 現実の乖離** | 参照先を改変すると落ちる |
| 分岐検査 | **レコード間の乖離** | 1本だけ直し忘れると落ちる |

**この2つは冗長ではない。** 参照先を改変したとき、全レコードが同じ「古い」ハッシュを持つため分岐検査は通る。**故障モードが違う。**

**VR-12. 名称は書誌情報ではない。** 一般名は `common_name` に置き、`source_origin` は書誌情報（文献名＋式番号）が判明するまで `null` のままにする。

> `source_origin` が `null` の項目の一覧は、**文献を取り込むときの作業リストになる。** 名称で埋めてしまうと、このリストが消える。

## 登録形式

```jsonc
{ "key": "...",
  "form": "式そのもの（コードではなく数式）",
  "variables": { "記号": "意味と単位" },
  "common_name": "...",                  // 一般名。書誌情報ではない（VR-12）
  "source_origin": null,                 // 文献名 + 式番号。不明なら null（VR-12）

  "source_refs": [ ... ],                // 参照とハッシュの集約（VR-11, VR-11a）

  "basis": "published",
  "validity_range": { ... },             // 必須。不明なら null（VR-1, VR-2）
  "validity_gate": null,                  // 解除条件。書けなければ null（VR-4）
  "validity_gate_ref": null,              // source_refs[].id

  "limitations": "範囲外で何が壊れるか",   // 原典に無ければ null
  "limitations_ref": null,                // source_refs[].id
  "limitations_basis": "explicit",        // explicit / inferred（VR-8）
  "limitations_inference": null,          // inferred の場合、推論経路を1行（VR-8）

  "limitations_candidate": null,          // 原典に無いが特定できた限界（VR-9）
  "candidate_basis": null,                // 通常 judgment（VR-9）
  "candidate_author": null,               // 誰が書いたか（VR-9）

  "note": "..."                           // 履歴情報など。validity_gate を混ぜない
}
```

**機械検査の対象**: `*_ref` が `source_refs[].id` に解決すること ／ 各 `sha256` が実ファイルと一致すること ／ 同一パスに複数のハッシュ値が現れないこと ／ 未知の欄と欠落欄がないこと ／ `limitations` が非 `null` なら `limitations_basis` が存在し、`inferred` なら `limitations_inference` が存在すること。

## 根拠の種別（`basis`）

| 値 | 意味 |
|---|---|
| `published` | 文献・規格・ハンドブックに記載 |
| `measured` | 自分で測定した |
| `judgment` | 自分の判断。根拠は経験・観察・設計上の選択 |
| `unverified` | 上記いずれでもない。**成果物生成に使わない** |

**VR-6. `judgment` を物性値に使わない。** 物性値は `published` / `measured` のみ。

> **VR-6 は禁止形で書く。** 許可リスト方式にすると、正当な用途が漏れる。実測例: ソルバの選択・境界値・ペナルティ係数は文献値ではなく設計上の選択であり、`judgment` が正しい。許可リストに「構成判断のみ」と書いていたため、これが漏れていた。

**VR-7. `judgment` という値を明示的に用意する。** 根拠欄に「勘で決めた」を正直に書ける値がないと、人は自分の判断を `published` と書く。**記録が嘘になるほうが、正直な `judgment` より有害である。**

## 登録しない判断

**VR-13. 登録しても情報量がゼロなものは登録しない。** 判断基準:

- 教科書・ハンドブックに普遍的に載っており、失っても即座に再取得できる
- **かつ** `limitations` が原典に存在しない

この両方を満たすものは、登録しても「式」しか残らない。**curate する価値は式ではなく限界の記述にある。**

**VR-14. 登録しないと判断したものは、判断記録に残す。** 理由を書かずに除外すると、後で同じ検討が繰り返される。
