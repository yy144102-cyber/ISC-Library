## 新規指摘 — セキュリティ層（S系）

**S-1 (High) 防御はヒューリスティックであり回避可能**
scan_for_injection は既知パターンのみ。Base64/同形異字/言語切替/婉曲表現で素通りする。
wrap_untrusted の遵守はLLM次第で、モデル更新で耐性が変わり得る。
→ 判定: これらを「壁」と誤認しないこと。設計上も docs/05 で減衰装置と明記済みだが、
  実効的な安全は権限分離側にある。**確認ゲートは現状「方針定数」でありコネクタ未実装の
  ため執行コードが存在しない**。Phase 5でUIゲートを実装するまでV5系の防御は紙上。

**S-2 (High) 生成コード実行にOSサンドボックスがない**
coderのsubprocessはユーザー権限で走る。現状は「ユーザー自身が依頼したコード」だが、
data_analyst 実装（Phase 2）で「外部ファイル→コード生成→実行」の間接インジェクション
経路が**完成**する。timeoutは資源防御であり権限防御ではない。
→ 要求: Phase 2 で data_analyst を実装する際、コンテナ/低権限ユーザー/ネットワーク遮断の
  いずれかを同時導入すること（ロードマップに反映済み）。

**S-3 (Med) LessonGateは意味的な毒を検出できない**
「もっともらしいが有害な教訓」（例: 特定条件で検証を軽くする趣旨の巧妙な文）は通過し得る。
テストで骨抜き系パターンは1種弾けることを確認したが、言い換え耐性はない。
→ 緩和: lessonsのUI常時可視+削除機能（実装済の閲覧に削除を追加）、件数上限、人間監査前提。

**S-4 (Med) 防御の回帰試験が最小限**
test_security.py は基礎のみ。モデル更新・プロンプト変更で耐性が劣化しても検知できない。
→ 攻撃サンプル集（難読化含む）をtests/fixturesに蓄積しCI必須化。

## 新規指摘 — 物理コア（P系）

**P-1 (High — 絶対値利用に対して) 第一次近似モデルの限界**
- 上昇損失が定数推定（±数百m/sの不確かさ）。軌道積分なし
- Isp一定近似: 初段の海面→真空変化を平均値で代表（利用者が平均Ispを与える責任がある）
- eps一定: 段規模・推進剤種依存のスケール則を無視。フェアリング・残留推進剤・
  ウルッジ/マージン方針も未導入
→ 判定: **相対比較・クロージャループ骨格・アーキテクチャ検証には妥当**（コード内・
  モジュールdocstringに適用範囲を明記済み）。要求確定や機体コミットに単独使用してはならない。
  6cゲート: 軌道3DOF積分・質量マージン方針・eps根拠データの3点が揃うまで高忠実度化に進まない。

**P-2 (Med) ΔV配分最適化は大域最適の保証なし**
SLSQP+多スタート(4点)で緩和したが保証はない。ペナルティ形状（1e9×不成立度）に依存。
→ 緩和: 均等割との比較検査をテストに組込済。3段以上ではグリッド初期化の追加を推奨。

**P-3 (Low) 数値検証の範囲**
導出式はΔV逆算のroundtripで機械検証済（誤差<1e-9）。ただし実在機体との突合
（公開諸元でのサニティチェック）は未実施 → 6aの受入試験として推奨。

## 新規指摘 — 統合（I系）
**I-1 (Med)** rocket_system は同期実装。6aでは問題ないが、6bで gen_design 子run
（将来はFEM評価）を接続した瞬間に #1（ジョブ層）への依存が復活する。順序厳守。
**I-2 (Low)** UIに階層run・objectives の表示がなく、多目的結果はJSONを直接見る状態。
**I-3 (Low)** LLMによるミッションJSON抽出経路は実疎通未検証（構造化入力経路のみテスト済）。

## 検証エビデンス
pytest 15件全緑（防御6・物理/モジュール6・骨格3）。導出式roundtrip・最適化非劣化・
汚染教訓の永続化拒否・境界トークンのランダム性を機械検証。

## 総合判定
v0.2 は **6aの意思決定支援とアーキテクチャ検証に耐える**。セキュリティは多層化されたが
「減衰装置」であり、実効的安全は権限分離の実装（Phase 2サンドボックス・Phase 5確認ゲート）
に懸かっている。優先順位: ①S-2をPhase 2の必須要件に格上げ（済） ②#1ジョブ層（Phase 4）
③Phase 5初手の接続PoC＋ゲート執行実装 ④P-1の6cゲート厳守。
