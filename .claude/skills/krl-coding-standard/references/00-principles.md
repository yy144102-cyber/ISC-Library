# 設計原則（P1〜P6）

条項を追加・却下・解釈するときの判断基準。条文そのものではない。
**根拠のない原則は入れない。** 各原則には実際に起きた失敗を付ける。

---

## 目的: シンプルに、素直に書く `確定`

原則 P1〜P6 は「何を防ぐか」。その上にある「何を目指すか」がこれ。

- 同じことができる選択肢が複数あれば、**仕組みが少なく、KUKA の想定した使い方に近い方**を選ぶ
- こちらから複雑にしない。KUKA の命令（ArcTech を含む）は素直に使う
- 手元の問題（読みにくい、分かりにくい）は、仕組みを作り替えるより、書き方の工夫を積み重ねて解く
  （例: WDAT の Channel を一覧表にして起動時に代入する。WDAT 自体はやめない）

---

## P1. 暗黙に依存しない `確定`

既定値、省略時動作、直前の状態、読み手の推測に結果を委ねない。

コントローラに対する暗黙（初期値依存）と、読み手に対する暗黙（名前から
単位が読めない）を同じ原則で扱う。どちらも「書かれていないことに結果が
依存する」構造だから。

**根拠となった実例**

- `MotionPar(#CPmotion,…)` を呼ばずに `LIN` を実行。`$VEL.CP` が
  `BAS(#INITMOV,0)` の初期値のままで、AUTO で A4 速度超過により停止
- `LIN_REL` に `#BASE` / `#TOOL` を書かず、既定がどちらか不明のまま運用
- `MotionPar` の引数が CASE によって % と m/s で変わる。呼び出し側から
  区別がつかない
- `TS`（mm/min）と `Velocity`（m/s）が単位表記なしで同居

---

## P2. 単一の真実源 / 複製耐性 `暫定`

同じ概念を2箇所に書かない。書かざるを得ないなら片方を導出にする。
**複製せざるを得ない処理は、複製しても壊れない構造にする。**

系（いずれも暫定）:

- 共有処理は引数で完結させ、外部状態に依存しない
- 複製した場合、複製元を記録する（P5）
- 動作確認前の共通化は行わない。ただし先送りであることを記録する

**根拠となった実例**

- 溶接速度が `WDAT.Weld.Velocity` と Master の `Velocity` で二重管理。
  WV 系では前者が使われていない
- `Weave.Length × Frequency = TS` の従属関係が式ではなく手計算で維持
- `MotionPar` / `WeldingAct` / `VelocityCalc` が11ファイルにコピペされ、
  `VelocityCalc` の ELSE 値がファイルごとに違う
- `CircD2015_10RadiusChange01.src` が無印版と diff 完全一致。パラメータを
  処理部に直書きしたためファイルごと複製された
- `MotionPar` が `PPDAT1` / `LCPDAT1` / `FP1` を暗黙参照。別モジュールへ
  コピーすると静かに壊れる

---

## P3. 状態は状態として持つ `確定`

値から状態を逆算しない。

**根拠となった実例**

- `SegFlip()` が `WV_SEG2.Y <> 0.0` で進行方向を推定。X進行モードでも
  この条件が真になり、ELSE が到達不能。判定条件が値域と結合している

実例は1件だが構造的な問題で、同じ書き方は今後いくらでも生まれる。

---

## P4. 静かに失敗させない `確定`

効果のない記述、通らない分岐、未初期化を残さない。

**根拠となった実例**

- `VelocityCalc` の IF と ELSE が同一式。分岐の意味が失われたまま残存
- `LIN_REL START_OFS` が `SX=SY=SZ=0` でゼロ長動作
- `IF NOT DryRun THEN` の中身がコメント1行のみ（空ブロック）
- 導出値を `.dat` に置くと、初期化処理を飛ばしても前回の値で動いてしまう
- `REAL` → `INT` の引数転送は黙って四捨五入される（S13）

---

## P5. 検証状態を明示する `確定` **恒久**

値・仮定・動作について、**どこまで確かめたか**をコードと文書に残す。

「動いた」と「正しい」を区別する。実機に触れない期間は特に重い。
`;@ASSUME` タグ（N10）がこの原則の実装。

**根拠となった実例**

- `$OUT[9]/[10]` を「立てられていない」と断定したが、SPS.SUB / PLC 側は未確認
- `POS_HOME` の S/T を他プログラムからコピー。出所と妥当性が失われている
- DryRun を T1 で検証して「意図通り」と判断。AUTO で停止
- Base17 の値が外部キネマティクス割付と整合しているか未確認のまま運用

---

## P6. 実行の前後で状態を壊さない `確定`

プログラムが変更したコントローラ状態は、戻すか、変更したことを明示する。

P1 が「読む側」、P6 が「書く側」。両方揃わないとプログラム間の状態リークは
防げない。

**根拠となった実例**

- 旧 W3D コードが `BASE_DATA[17]` を実行時に上書きし、終了時に戻していない。
  1回流すと Base17 が別物のまま残る
- `SegFlip()` が `.dat` の `WV_SEG1/2` を書き換えたまま終了

---

## 優先順位 `暫定`

**P1 > P4 > P2 > P6 > P3 > P5**

理由は「破れたときの被害の大きさ」。P1 の違反は装置を停止させ（実際に停止
した）、P5 の違反は判断を誤らせるだけで直接は壊れない。

条文を書いてみて衝突が出たら見直す。

### 衝突したときの裁定

| 衝突 | 裁定 |
|---|---|
| P1（明示）vs 簡潔さ | 明示を優先。冗長でも書く |
| P2（導出）vs P1（明示） | 導出は P1 に反しない。ただし導出は1箇所にまとめ、式をコメントで示す |
| P6（状態を戻す）vs 中断復帰 | 復帰のために状態を残す場合は、意図的に残していると明記する（P5） |
| P2（共通化）vs 切り分けやすさ | 動作確認前の共通化は行わない。先送りであることを記録する |

---

## メタ規則: 機械検査できる形で書く `確定`

条文を書くたびに「`krlcheck.py` で検査できるか」を判定する。

- 検査できる → 検査項目に落とす
- 検査できない → 条文は書くが「**目視確認項目**」と明記する

実機もコンパイラも使えない期間、`krlcheck.py` が唯一のフィードバック
ループになる。ここを曖昧にすると規約が形骸化する。

---

## 原則にしないもの

後から「一貫性のため」という理由で紛れ込むのを防ぐため、明示的に除外する。

- **既存コードとの一貫性** — 既存コードの正しさが担保されていない以上、
  一貫性は根拠にならない
- **短く書く** — P1 と正面から衝突する。短さは目的ではない
- **KUKA のインラインフォームが生成する形に合わせる** — 生成物は参考情報で
  あって規範ではない。ただし生成物を手編集しないことは別途の制約
