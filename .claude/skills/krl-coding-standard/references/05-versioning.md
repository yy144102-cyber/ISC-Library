# ファイル命名と版管理（V1〜V8）

---

## 前提: コントローラ側に版の概念がない `確定`

実機のプログラム一覧は**フラットなファイル名だけ**。フォルダ階層はあるが、
版・分岐・履歴を持つ仕組みはない。`&REL` はエディタが増やす保存回数の
カウンタで、こちらが管理する版番号ではない。

**したがって「実機に載っているのがどの版か」は、ファイルの中身を見ないと
分からない。** ここが版管理の設計の出発点。

---

## V1. ファイル名は `<機能名>_<YYYYMMDD>` `確定`

```
WBead_20260924.src / WBead_20260924.dat
WBead_20260924a.src          ← 同じ日の2版目。末尾に小文字1字
```

**日付は入れる。造形条件は入れない。**

| 悪い | 理由 |
|---|---|
| `WBead` | 日付が無い。フォルダの一覧でいつのコードか分からない |
| `CircD2015_10RadiusChange01` | 条件（半径）が名前に入っている |
| `ISC_CladdingSquare_t15` | 条件（t15）が名前に入っている |

**根拠**:
- 日付 — フォルダを一覧したとき、いつのコードかが名前で分かる（運用上の要求）
- 条件の禁止 — 条件を名前に入れると、条件を振るたびにファイルが枝分かれする。
  実際 `CircD2015_10RadiusChange01.src` は無印版と diff 完全一致だった。条件はパラメータで振る（V4）

**制約**:
- `DEF` / `DEFDAT` の名前もファイル名と同じにする（N12）。したがって識別子の 24 文字制限（N1）がファイル名に掛かる。
  日付部分 `_YYYYMMDD` で 9 文字使うので、**機能名は 15 文字以内**
- 接頭辞は日付を除いた機能名から導く（`WBead_20260924` → `WB_`）
- **他のプログラムから呼ばれるモジュールには向かない。** 版を上げるたびに名前が変わり、呼び出し側を全部書き換えることになる。
  トップレベルの造形プログラムには適用し、共有モジュール（`CM_` 系）の命名は S5 で分割を検討するときに決める `保留`

### 版を上げる単位 `暫定`（2026-09-29 改訂）

**版（ファイル名の日付）は造形パスに付ける。条件値には付けない。**

| 変えたもの | 造形前（空走行・調整） | アークを出して造形したあと |
|---|---|---|
| `.src` の命令（パスの生成、動作の順序、アークや RSI の呼び方） | 同じ名前のまま直してよい | **新しい日付の版にする** |
| `.dat` の宣言の構成（変数の追加・削除・型の変更） | 同上 | **新しい日付の版にする**（`.src` と対で変わるため） |
| `.dat` の値（WFS、TS、上げ幅、層数、開始点、ウィービングの形など） | 変えてよい | **版を変えずに変えてよい。** 造形ごとに記録する（V8） |
| コメント、ヘッダの VERIFIED | 変えてよい | 版を変えずに変えてよい |

見分け方: `.src` の差分がコメントの行（`;` で始まる行）だけなら、動作は変わらない。命令の行が1行でも変われば、新しい版にする。

新しい版にするときは、`DEF` / `DEFDAT` 名も合わせる（N12）。空走行は「造形」に含めない。

**根拠**:
- 条件値は、造形しながら振るのが仕事。値を変えるたびに版を上げると、値だけ違うクローンが増える（V4 と矛盾する）
- T8 は、アークを出したあとの段階（6〜7）を VERIFIED に書くよう求めている。旧 V1 のままでは書けなかった
- 造形物からさかのぼるときは、版（パス）と造形の記録（値、V8）の2本でたどる

旧 V1（「アークを出して造形したファイルは凍結し、変更は新しい日付のファイルで」）は撤回した（`91-open.md`「撤回した判断」）。

### 新しい版の作り方 `暫定`（2026-09-29）

1. 前の版の `.src` / `.dat` をコピーし、ファイル名を `<機能名>_<YYYYMMDD>` にする
2. 中の `DEF` / `DEFDAT` 名をファイル名と同じにする（N12）
3. ヘッダの `VERSION` を新しくし、**`VERIFIED` は全段階を `---  not yet` に戻す**
4. 変更を入れ、`krlcheck` を通す
5. 前の版との差分を見て、変えたのが意図した所だけかを確かめる

**根拠**:
- 新しい版は「前の版 ＋ 変更」。書き直すと、実績のある細部（`WDAT1` の上書きを最初の動作より前に置く、ARC の行は手で変えない、など）を黙って落とすおそれがある。コピーなら、変えない部分は実績のまま残る
- `VERIFIED` を戻すのは、前の版の検証は新しい版の検証にならないから（T8）。コピーしたまま残すと、未検証の版が検証済みに見える

現地で改名すると、`DEF` / `DEFDAT` 名の直し忘れ（N12）を踏みやすい。改名は落ち着いた環境で行う。

**改訂履歴**: 当初は「日付・版番号を名前に入れない。版はリポジトリで持つ」としていたが、
フォルダの一覧で日付を見たいという運用上の要求と、`DryRun_20260915` がこの形で動いている実績から改めた。

## V2. 版はリポジトリで持つ `確定`

履歴・分岐・差分は git（または Notion）で管理する。ファイル名の日付（V1）は「いつの版か」を一覧で見るためのもので、
何を変えたかはリポジトリに残す。

実機とリポジトリの役割:

| | 持つもの |
|---|---|
| リポジトリ | 全履歴、差分、どの変更が何を直したか |
| 実機 | **現在動いている1つ** |

---

## V3. 実機に載せた版を特定できるようにする `確定`

ファイル名の日付（V1）で「いつの版か」は分かるが、同じ日付の中でどの変更が入っているか、
リポジトリのどのコミットかまでは分からない。

**ヘッダに版識別子を書く。**

```krl
DEF WBead( )
;=============================================================
; WBead - weaving bead deposition
;
; VERSION  2026-09-22  <commit hash or Notion page version>
; VERIFIED
;   stage 0-1  2026-09-22  krlcheck ok / compiled ok
;   stage 2    ---         not yet
;=============================================================
```

`krlcheck.py` で「`VERSION` 行があるか」「リポジトリの HEAD と一致するか」を
検査できる（メタ規則）。

`暫定`: 識別子の形式（コミットハッシュか日付か連番か）は運用してから決める。
**重要なのは「実機のファイルから遡れること」**であって、形式ではない。

## V4. 派生ファイルを作らない `確定`

条件違いのために `.src` を複製しない。**パラメータで振る。**

```
NG : WBead_step13_20260924.src / WBead_step14_20260924.src
OK : WBead_20260924.src + WB_layerStepMm を変える
```

どうしても構造が違って複製が要る場合（造形方式そのものが別など）は、
**モジュールとして分ける**（`WBead` / `SBead`）。接頭辞も分ける（N2）。

その場合でも、共通部分の複製には複製元を記録する（P2）。

---

## V5. アーカイブを取るタイミング `確定`

実機のアーカイブ（`.zip`）は、リポジトリとは別に**コントローラ全体の
スナップショット**として取る。`BAS.SRC` / `$CONFIG.DAT` / `$MACHINE.DAT` /
安全構成 / 外部キネマティクス設定が入っており、**これらはリポジトリに
入っていない**。

取るタイミング:

- **動いている状態を確認した直後**（壊す前の基準点）
- ベース／ツールの再計測の前後
- 安全構成・機械データを変更する前
- インテグレータが作業した後
- Phase を上げる前

**「壊れてから取る」では意味がない。** 動いていた状態が残らない。

---

## V6. `&REL` と `&ACCESS` を手で変えない `確定`

ヘッダ行はコントローラとエディタが管理する。

```
&ACCESS RVP
&REL 154
```

`&REL` は保存回数のカウンタ。手で書き換えると実機との対応が壊れる。
**版管理には使わない**（V3 のヘッダコメントを使う）。

`&PARAM KRL_MODEL_IGNORE = TRUE` などの `&PARAM` 行は意味が未確認
（`91-open.md`）。既存ファイルから引き継ぐ場合は、**引き継いだという事実を
コメントに残す**（P5）。

---

## V7. 実機へ載せる手順 `暫定`

1. `krlcheck.py` を通す
2. コンパイルする
3. **アーカイブを取る**（V5。上書き前の状態を残す）
4. ヘッダの `VERSION` を更新してからコミット
5. 実機へ転送
6. `VERIFIED` 行を段階に応じて更新（T8）

`暫定`: 転送手段（WorkVisual / USB / ネットワーク）と権限が未確認。
実機に触れてから確定させる。

## V8. 造形ごとに記録する `暫定`（2026-09-29 新設、2026-10-05 改訂）

`.dat` の値は版を変えずに変えてよい（V1）。その代わり、造形ごとに値を記録する。

### 1造形の範囲

**1造形 ＝ 同じ条件（`.dat` の値）のまま、造形プログラムを1回完遂すること。** 途中で止めて同じ条件で再開しても、日をまたいでも1造形。
途中で区切るのは次の2つ。どちらも、そこまでを1造形とする。

| 区切り | 結果 | そのあと |
|---|---|---|
| 最後まで行かずにやめた | 「途中で中止」 | — |
| 途中で `.dat` の値を変えた | 「値を変えて続行（次の ID へ）」 | 続きは新しい造形 ID で、別の造形として記録する |

結果を2つに分けるのは、失敗してやめた造形と、値を変えて積み続けた造形を区別するため。空走行は造形に含めない（V1）。

プログラムの外の条件（集塵の方式など）を途中で変えたときは、区切らずに「途中の出来事」として書く。

例: 2026-09-25 は、1枚の母材にプログラムを4回完遂して壁を4本積んだ。これは4造形（WAAM-1-1〜WAAM-1-4）。
4本目は高さ 100 mm で集塵をエンドエフェクタに切り替えた。これは `.dat` の値の変更ではないので、これだけでは区切らない。

### 造形 ID は `WAAM-<案件番号>-<連番>`

- 案件番号: Notion の案件 DB の番号。再稼働後（2026年7月〜）の案件に 1 から振る（2026-09-25 の試作が 1）
- 連番: その案件で何回目か（1 から）
- 造形物（母材）にも同じ ID を書く
- 再稼働前の案件は `WAAM-Pre<旧番号を2桁>`（WAAM-Pre01〜15）。Notion の「資料台帳（再稼働前）」に、案件ごとの概要（種類「造形概要」）と資料がある。造形ごとの ID は持たない
  - 2桁にするのは、台帳で案件ID ごとにまとめたとき、名前の順が番号の順になるようにするため（Pre1 の次に Pre10 が来ない）。物品品目マスターの分類（01〜14）と同じやり方

**根拠**:
- 案件番号を入れると、造形物の ID から案件がたどれる
- 再稼働前と形を変えるのは、前後を ID だけで見分けるため。旧番号は 2026-02 に、造形が終わったあとで仮に付けたもので、ID として使うつもりのものではなかった
- 日付を入れない: 1造形は日をまたぐことがあり、日付では1つに決まらない。日付は作業日誌の側で持つ

### 記録すること

| 項目 | 例 |
|---|---|
| 形状 | 1ビード、平壁、円筒、部品名 |
| 版 | `WBead_20260924` |
| `.dat` の値 | WFS、TS、上げ幅、層数、層間の待ち、ウィービングの形、開始点 |
| 前の造形から変えた値 | `WB_layerStepMm 1.5 → 1.4`、`WB_posStart` の X `-7.0 → 30.5` |
| プログラムの外の条件 | ガスの種類と流量、ワイヤのロット、母材、集塵の方式 |
| 途中の出来事（時刻つき） | 高さ 100 mm で集塵をエンドエフェクタに切り替え |
| 結果 | 完了・途中で中止・値を変えて続行のどれか、積めた層数、実測値と測り方、写真 |

- **1造形の `.dat` の値は1組だけ。** 途中で変えたら、そこで造形を区切る（1造形の範囲）
- **区切ったあとの造形の層数は 1 から数える。** 指令・完了とも、その造形の中の層の数を書く
- **「前の造形から変えた値」は、同じ案件・同じ版の直前の造形との差を書く。** 無ければ「初回」。途中で区切ったときは、区切る前の造形との差になる
- 室温・湿度など、その日の環境は作業日誌に書く

**根拠**:
- 2026-09-25 の造形では、壁4本の高さは記録したが、それぞれをどの値で作ったかは記録しなかった。
  実機の `.dat` には最後の値しか残らず、写しも取り込んだ時点の状態しか残さないので、あとから値を知る手段が無かった
- 値を変えたら区切るのは、1つの欄に値を1つしか書けないから。区切れば、どの層をどの値で積んだかが行で分かる
- 形状を書くのは、日付を覚えていなくても、何を積んだかから造形を探せるようにするため
- 差を同じ版の中で取るのは、版が変わるとパス（命令）が変わり、値の差だけでは何を変えたか言えないから

### 置き場所は Notion の「造形」DB

| DB | 単位 | 書くこと |
|---|---|---|
| 造形 https://app.notion.com/p/0a9c48d82d3f487faa2ec029e3ca9fe6 | 1造形1行 | 上の表。案件・作業日・使用ロット・トラブルにつなぐ |
| 作業日誌 https://app.notion.com/p/b0f8e021953e4cf7abc4f7d8dd8407da | 1日1ページ | その日の環境と所見。その日の造形につなぐ |

**根拠**: 造形 DB は、このセルのすべての案件の造形を1か所に持つ。置き場所はプロジェクトではなくセルで決まる。

**Notion には git のこと（フォルダ、写しの場所、コミット）を書かない。** git とのつながりは git の側に持たせる。

- 案件とプロジェクト: プロジェクトの `CLAUDE.md` に、案件ページの URL を書く。案件ページの ID で検索すればプロジェクトが見つかる
- 造形と実機の写し: 写しを取り込むコミットの件名に、その日の造形 ID を書く（`ref/KUKA_3261646/README.md` の「取り込み方」）。造形 ID から `git log --grep` で写しを探せる

**根拠**: Notion を見る人は、運用者のほかはローカルのファイルも git も見ない（2026-10-05 運用者確認）。git の場所を書いても、ほかの人には意味が通じない。

Notion の DB の説明と項目の説明にも、1造形の範囲と ID の決まりを書いてある。Notion で記録する人は Library を見ないので、Notion 側だけで分かるように書き、V8 には触れない。
**決まりを変えるときは、この V8 と Notion の説明の両方を直す。** 食い違いを機械で見つける手段は無く、読んで見つけるしかない。

`暫定`:
- 造形 ID は、2026-09-25 の4回にあとから付けただけ。造形の前に付けて使ったことはまだ無い
- 写しのコミットの件名に造形 ID を書き忘れても、機械では気づけない。検査のフックは、困るまで作らない（workspace.md R9）
- 写しは1日の終わりに1回なので、同じ日の造形ごとの値は写しに残らない。値は Notion の造形 DB に書く（上の「記録すること」）
