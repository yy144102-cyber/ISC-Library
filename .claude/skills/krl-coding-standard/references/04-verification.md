# 検証手順（T1〜T8）

> 条項番号の `T` は Test の T。オペレーティングモードの T1 / T2 とは無関係。
> 紛らわしいので、モードを指すときは必ず「モード T1」と書く。

---

## T1. 何を何で検証できるか `確定`

**検証の種類ごとに、使える手段が違う。** ここを混同したのが DryRun の失敗。

| 検証したいこと | 使える手段 | 使えない手段 |
|---|---|---|
| 構文・識別子の実在・型 | コンパイル（WorkVisual） | 目視、`krlcheck.py` |
| 規約準拠・タグ残存・未使用宣言 | `krlcheck.py` | コンパイル |
| 経路形状・教示点の妥当性・干渉 | **モード T1** | コンパイル |
| ロジック（分岐・層数・方向反転） | モード T1 | コンパイル |
| **速度・加速度・軸速度超過** | **AUTO のみ** | モード T1 |
| **特異点の通過** | **AUTO のみ**（低 POV から） | モード T1 |
| 先行実行の追従 | AUTO のみ | モード T1 |

### モード T1 は動特性を検証できない `確定`

モード T1 は TCP 速度がクランプされる。したがって

- 速度起因の問題（`$VEL.CP` 未設定、指令値過大）
- 特異点近傍で軸速度が発散する問題

の**両方をマスクする**。

**「モード T1 で意図通り動いた」は「ロジックと経路の順序が正しい」までしか
意味しない。** 動特性は未検証として扱う。

`暫定`: クランプ値そのものは安全構成で決まる。実機で確認する。

---

## T2. 段階 `確定`

上から順に通す。**飛ばさない。** 前の段階で落ちたら、直してその段階からやり直す。

| # | 段階 | モード | POV | 主眼 |
|---|---|---|---|---|
| 0 | `krlcheck.py` | — | — | 規約準拠、タグ残存 |
| 1 | コンパイル | — | — | 構文、識別子の実在 |
| 2 | 単層・空走行 | T1 | 低 | 経路形状、干渉、教示点 |
| 3 | 単層・空走行 | AUTO | **10%** | 動特性の初回確認 |
| 4 | 単層・空走行 | AUTO | 30 → 50 → 100% | 速度を段階的に上げる |
| 5 | 全層・空走行 | AUTO | 100% | 先行実行の追従、累積ずれ、所要時間 |
| 6 | 単層・アークあり | AUTO | 100% | 溶接条件 |
| 7 | 全層・アークあり | AUTO | 100% | 本番 |

Phase との対応: 段階 2〜4 が Phase 1、段階 5 が Phase 3、段階 6〜7 が Phase 4。

---

## T3. POV の上げ方 `確定`

段階 3〜4 は **POV 10% から始めて、10 → 30 → 50 → 100 の4段**で上げる。

各段で完走してから次へ。**途中で止まったら、そこが限界点。** 次の段には
進まず原因を切り分ける。

### 切り分けの原理

| 症状 | 意味 |
|---|---|
| 低 POV では通り、高 POV で落ちる | **速度起因**。指令値または加速度を下げれば解決する |
| 低 POV でも落ちる | **幾何起因**（特異点、到達範囲外）。速度では解決しない。経路を直す |

これが「モード T1 で通ったのに AUTO で落ちる」を再発させないための唯一の
手順。POV を段階的に上げること自体が切り分けになっている。

---

## T4. 記録項目 `確定`

各段階で以下を記録する。記録しない試行は**やっていないのと同じ**（P5）。

| 項目 | なぜ |
|---|---|
| 日時 | |
| プログラムの版識別子（V3） | どのコードを流したか特定できないと再現できない |
| モード / POV | 段階の特定 |
| 完走したか、止まったならどの行 | |
| エラーメッセージ（番号と全文） | KSS の番号は検索できる |
| そのときの `$POS_ACT` | 中断位置。M8 の観点で必須 |
| `$AXIS_ACT`（止まった場合） | 特異点の判定に要る |
| 所要時間 | 見積もりとの差 |
| 変更点（前回の試行との差分） | 1回に1つだけ変える |

### 1回に1つだけ変える `確定`

落ちたときに複数箇所を同時に直すと、どれが効いたか分からなくなる。
原因の特定が目的なので、変更は1つずつ。

---

## T5. 打ち切り条件 `確定`

以下に当たったら、その場で止めて再設計に戻る。粘らない。

- **同じ箇所で3回落ちた。** 対症療法を重ねている状態
- **低 POV でも落ちる。** 速度の問題ではないので、POV をいじっても無駄
- **原因が特定できないまま「なぜか通った」。** 断続的な不具合は設定ミスでは
  なく動的な状態に起因する。放置すると本番で再発する
- **エラー番号が調べても出てこない。** インテグレータに問い合わせる

---

## T6. モード T1 でやるべきこと `確定`

動特性を検証できないからといって、モード T1 が無意味なわけではない。
**モード T1 でしかできないことがある。**

- 教示点が想定の場所を指しているか（目で見る）
- 経路が治具・ワークに干渉しないか
- 層の方向反転が意図通りか
- 積層ピッチの向きが正しいか（上に積むか下に潜るか）
- アークを出す前に、トーチ姿勢が母材に対して妥当か

**段階 2 を飛ばして AUTO に行かない。** 干渉は速度に関係なく起きる。

---

## T7. 変更後の再検証 `確定`

コードを変えたら、**どの段階からやり直すか**を変更の種類で決める。

| 変更した内容 | 戻る段階 |
|---|---|
| コメント、命名のみ | 0 → 1 |
| `.dat` のパラメータ値（速度・加速度） | 3 |
| `.dat` の教示点 | 2 |
| 幾何の導出式、動作命令の追加・削除 | 2 |
| 動作種別の変更（LIN ↔ PTP） | 2 |
| 層数・繰り返し数のみ | 5 |

パラメータを変えただけでも段階 3 に戻るのは、**速度を上げると動特性が
変わるから**。T3 の切り分け原理がそのまま効く。

---

## T8. 検証状態をコードに書く `確定`

そのコードがどこまで検証されているかを、ファイルのヘッダに残す。

```krl
; VERIFIED
;   stage 0-1  <date>  krlcheck ok / compiled ok
;   stage 2    <date>  T1, path ok, no interference
;   stage 3    <date>  AUTO POV 10%, completed
;   stage 4    ---     not yet
```

`@ASSUME` と同じ発想（P5）。**「動いた」と「どこまで動いたか」を区別する。**

次に触る人が段階 4 を飛ばすのを防ぐのが目的なので、**通らなかった段階も
書く**。空欄ではなく `---  not yet` と明示する。
